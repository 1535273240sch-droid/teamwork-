# Teamwork 机制说明 & 与你现有 orchestrate 的关系

这份文档回答两个问题：

1. **Teamwork 到底"强制"了什么？** 哪些是运行时物理拦截的，哪些只是写在提示词里、靠 agent 自觉。
2. **它和你已有的 `orchestrate` skill 是什么关系？** 怎么配合，什么时候用哪个。

---

## 一、把"强制"拆开看

"多智能体框架"这个词容易让人以为整个流程都被硬性约束了。**实际上只有一部分是真的强制。**

| 机制 | 谁在执行 | 是不是真强制 |
|---|---|---|
| **文件独占锁**（`Edit` / `Write`） | `PreToolUse` 钩子 `ownership-lock.mjs` | ✅ **真强制**——物理拦截，写不进去 |
| **文件独占锁**（shell 写入） | `PreToolUse` 钩子 `bash-guard.mjs` | ⚠️ **部分覆盖**——认得出目标文件就拦，认不出就放行 + 警告（见下） |
| **锁的临界区原子性** | `mkdir` 互斥（`_lib.mjs`） | ✅ **真强制**——并发认领不会互相覆盖 |
| **角色隔离**（独立上下文 + 独立工具权限） | ZCode subagent 运行时 | ✅ **真强制**——Critic/Auditor 拿不到 Edit/Write 权限 |
| **每轮验证 + 自动继续** | Goal Mode | ✅ **真强制**——ZCode 运行时行为，不靠 agent 记性 |
| **只认真实证据** | Goal Mode 的验证器 | ✅ **真强制**——不认计划、不认总结 |
| **宪章 + 计划跨会话注入** | `SessionStart` 钩子 | ✅ **真强制**——每次新会话自动注入（matcher 用 `*`，任何 source 都覆盖） |
| **验证产物存在** | Goal Mode 的 `/goal` 判定条件 | ✅ **真强制**——`verifications/` 和 `final-audit.md` 不在，目标就不判定完成 |
| 规划先行 + 人工批准 | `/teamwork` 命令 + skill + **钩子激活门** | ⚠️ **半强制**——流程规定，且 `approved`/`phase` 两个字段同时成立钩子才武装 |
| **做和验分离**（谁做的不许自己验） | 验证产物 + 主 agent 的调度 | ⚠️ **半强制**——**产物被检查，"是谁写的"运行时看不见** |
| **四个验证问题全覆盖** | 验证产物 + 主 agent 的调度 | ⚠️ **半强制**——同上 |
| **终审对着宪章而不是里程碑** | `final-audit.md` + success-auditor | ⚠️ **半强制**——文件必须存在且结论为 `ACHIEVED`，但内容质量靠角色自觉 |

### 一句话总结

**真被强制的，是"物理动作"、"运行时行为"，以及"产物存不存在"；半强制的，是"这份产物是谁写的、写得诚不诚实"。**

- 文件锁、权限、Goal Mode 验证、宪章注入、验证产物存在性——**你不配合也躲不掉**
- "派一个没参与实现的 agent 去验"——**现在它的产物被运行时检查了，但运行时不知道是谁写的**

**所以：这套框架把"你被骗的概率"从"显著"压到了"低"，但没有压到零。** 剩下的那条缝是：主 agent 可以自己写一份验证记录冒充验证角色。堵这条缝需要 `PostToolUse` 钩子去比对写入者身份——而身份归属本身就不完整（见下），现在做不到。

### ⚠️ 两个必须说清楚的洞

**洞一：shell 写入的覆盖是不完整的。**

`bash-guard.mjs` 不解析 shell，它做模式匹配。`> file`、`tee`、`sed -i`、`dd of=`、`rm`、`mv`、`cp` 的目标能认出来；**变量、通配符、命令替换、`find -exec`、脚本内部的写入认不出来**。认不出的一律放行 + 警告，不会误拦。

唯一可靠的路径是让 Worker 用 `Edit` / `Write` 改源码。这条已经写进 `worker.md` 的硬约束和 `critic.md` 的检查清单（Critic 用 `git diff` 核对改动来源）。

**洞二：持有者身份可能完全失效。**

归属链是 `TEAMWORK_OWNER_TOKEN` → `agent_id`/`agent_type` → `transcript_path` 哈希 → `session_id`。但 **ZCode 的钩子文档没有记载 `PreToolUse` 载荷里有 per-subagent 标识符**。如果确实没有、且 `transcript_path` 又是会话共用的，那么所有 Worker 解析成同一个 owner，冲突检查**完全失效**——不是"退化成先到先得"，是**零保护**。

钩子现在会**检测这个状态并明确告警**（形态为 `distributed-coding` 且归属落到最弱一档时，第一次认领就写一条警告进上下文）。

要精确归属，唯一可靠的办法是**一个 Worker 一个 ZCode 进程**，在那个进程的环境里设 `TEAMWORK_OWNER_TOKEN`。**注意：不是在派发子 agent 时设环境变量**——钩子是 ZCode 进程的子进程，继承的是 ZCode 的环境；子 agent 是进程内派发的，改不了它。

### 实践建议

用它的时候，**在访谈的"独立验证"那一栏里，把"由谁验"写死**（比如"必须由 critic 或 auditor 验证，且不许是 worker"），并把它写进**验收标准**。这样 Goal Mode 每轮验证时会拿它当标准，**从"靠自觉"变成"被检查"**。

再配合 `/teamwork-status`：它会把**没有验证记录的里程碑**点名列出来。

## 二、和 `orchestrate` 的关系

你已有的 `~/.zcode/skills/orchestrate/` 是一套**编排者-工人工作流**，六步：澄清需求 → 方案确认 → 拆分派活 → 逐个审查 → 整合 → 交付。

两者**不是替代关系，是不同层面的东西**。

### 相同的地方

- 都要求**先澄清再动手**（orchestrate 的"澄清需求" = Teamwork 的 Phase 1 访谈）
- 都要求**方案先给人确认**（orchestrate 的"方案确认" = Teamwork 的宪章批准）
- 都讲**拆分、并行、回传纪律、写冲突隔离**
- 都讲**成本意识**（你的 orchestrate 里写着"多智能体比单智能体贵约 90%"）

**说明你已经有一套成熟的多智能体方法论了。** Teamwork 不是来取代它的。

### 关键的区别：审查由谁做

这是两者最本质的分歧。

| | `orchestrate` | `Teamwork` |
|---|---|---|
| **谁审查** | **主 agent 自己**（它是编排者，它审） | **独立的 subagent** |
| **审查分几个角度** | "逐个审查"——一个通用检查 | **四个不同的角色，问四个不同的问题** |
| **审查者能看到什么** | 主 agent 的全部上下文 | 独立上下文，**且不信任实现者的报告** |
| **审查留痕** | 无 | **落盘成 `verifications/` + `final-audit.md`，被 `/goal` 检查** |
| **写冲突** | 靠纪律：worktree / 分支 / 独立子目录 | **靠钩子物理拦截**（编辑工具精确，shell 部分覆盖） |
| **目标收敛** | 靠主 agent 循环 | 靠 Goal Mode 每轮自动验证 |

**最关键的一条：`orchestrate` 的审查是主 agent 做的，那本质上还是"同一份判断的第二遍"。**

Teamwork 的 Auditor 是一个**独立上下文、独立工具权限、明确被要求"不信任 Worker 报告"**的 subagent。它会自己重跑一遍，对比数字，并把结论写进文件。

### 具体差在哪——一个例子

一个量化策略回测出高收益：

- **`orchestrate` 的审查**：主 agent 检查代码跑没跑通、对照验收标准看 diff。**它不会去怀疑"这个收益本身是不是真的"。**
- **`Teamwork`**：
  - **Challenger** 专门去查**这收益是不是来自未来函数、是不是在测试集上调参、基线是不是挑了个弱的**
  - **Auditor** 从干净状态重跑，看数字对不对得上
  - **Success Auditor** 问"当初要的是一个能上实盘的策略，还是一个漂亮的回测数字"

**`orchestrate` 不会帮你做这件事，因为它的审查者就是那个建东西的人。**

## 三、怎么配合用

### 实操建议

| 场景 | 用什么 |
|---|---|
| 日常复杂任务、拆分并行、需要多工人协作 | **`orchestrate`**——更轻，你已经用熟了 |
| 结论必须可信、答错代价高、你自己没法一眼验证 | **`/teamwork`**——四个独立验证角色值这个钱 |
| 跨几十个文件的重构 / 迁移 | **`/teamwork`**（Distributed Coding 形态） |
| 量化策略、实验结论、研究报告 | **`/teamwork`**（Challenger 是它最值钱的部分） |
| 单文件修复、小改动、几分钟的事 | **都别用**，直接做 |

### 一句话判断

> **如果这个结论错了、而你没法靠自己一眼看出来，用 `/teamwork`。否则用 `orchestrate`，或者干脆自己做。**

### ⚠️ 一个要注意的地方

**两者是两套独立的流程定义，不会自动叠加。** 主 agent 只会执行它认为你在要的那一个。

- 敲 `/teamwork` → 走 Teamwork 流程
- 说"按 orchestrate 的流程来" → 走 orchestrate 流程
- **不要指望"两个都生效"**——它们的步骤有重叠，同时执行会互相打架

## 四、装了什么、放哪了

0.2.0 起走的是**插件形式**（GitHub marketplace 分发），不再往用户级目录散装文件。理由在下面那张表里：项目级钩子被运行时整体忽略，所以钩子必须随插件走。

```
<插件安装目录>/
├── agents/                      ← 8 个角色
│   ├── sentinel.md              起点关卡
│   ├── orchestrator.md          拆解、依赖图、所有权表
│   ├── explorer.md              只读调研
│   ├── worker.md                实现
│   ├── critic.md                查实现的缺陷
│   ├── challenger.md            攻击前提
│   ├── auditor.md               独立复现证据
│   └── success-auditor.md       终审
├── skills/
│   ├── teamwork/SKILL.md        Phase 1：访谈与宪章
│   └── teamwork-execute/SKILL.md Phase 2：调度循环与升级协议
├── commands/
│   ├── teamwork.md              /teamwork
│   ├── teamwork-status.md       /teamwork-status
│   └── teamwork-end.md          /teamwork-end
└── hooks/
    ├── hooks.json               钩子注册（自动发现）
    ├── _lib.mjs                 共用的锁 / 租约 / 路径规范化
    ├── ownership-lock.mjs       编辑工具的文件独占锁
    ├── bash-guard.mjs           shell 写入守卫
    └── session-context.mjs      宪章与计划注入
```

### 运行时会写什么（在你的目标项目里）

```
<你的项目>/.teamwork/
├── campaign.json       宪章
├── plan.json           里程碑 + 依赖图 + 所有权表
├── ownership.json      当前租约
├── events.jsonl        认领 / 拒绝 / 过期事件
├── verifications/      每个里程碑的验证记录
├── final-audit.md      终审结论
└── history/            /teamwork-end 归档到这里
```

**把 `.teamwork/` 加进目标项目的 `.gitignore`。**

### 和"用户级目录"装法的区别

早先版本（0.1.0 之前）把文件散装到 `~/.zcode/` 下。现在统一走插件：

| | 用户级目录（旧） | 插件形式（现在） |
|---|---|---|
| 功能 | 一样 | 一样 |
| 出现在 Plugins 页面 | ❌ | ✅ |
| 一键开关 / 分享给别人 | ❌ | ✅ |
| 钩子能生效 | 要手改 `cli/config.json` | ✅ 随插件自动注册 |

### ⚠️ 从旧版用户级安装迁移过来（**必读**）

**如果你在 0.1.0 时代按上面的旧方式装过，那些文件必须清掉，否则装插件等于白装。**

原因是 ZCode 的钩子执行顺序是 **user Hook → 已启用插件 Hook**。旧版把钩子注册在 `~/.zcode/cli/config.json` 里，而那个 `ownership-lock.mjs` 是**没有互斥锁、没有批准门**的版本。它会**先于**插件的新钩子运行，于是：

| 你以为在用 0.2.0 | 实际上 |
|---|---|
| 批准之后才武装（#11） | 旧的先跑，**访谈期间就武装了** |
| 并发认领不会互相覆盖（#1） | 旧的先跑，**TOCTOU 竞态会覆盖掉新钩子写的认领** |
| shell 写入被拦（#3） | 旧的根本不知道有 `Bash` 这回事 |

而且两套钩子共用同一份 `.teamwork/ownership.json`，互相打架，认领记录不可信。

**迁移步骤：**

1. **先备份。** 至少覆盖 `agents/`、`skills/teamwork/`、`commands/teamwork.md`、`hooks/teamwork/` 和 `cli/config.json`。
2. **移除旧文件**（注意 `commands/` 和 `skills/` 里还有别的东西，**只删 teamwork 那几项，不要删目录**）：
   ```
   ~/.zcode/agents/{sentinel,orchestrator,explorer,worker,critic,challenger,auditor,success-auditor}.md
   ~/.zcode/skills/teamwork/
   ~/.zcode/commands/teamwork.md
   ~/.zcode/hooks/teamwork/
   ```
3. **摘掉 `~/.zcode/cli/config.json` 里的两条 teamwork 钩子**（`hooks.events.SessionStart` 和 `hooks.events.PreToolUse`），把 `hooks.events` 置成 `{}`。
   **`hooks.enabled` 必须保持 `true`**——它是钩子的总开关，删掉它连插件的钩子一起不生效。
4. **装插件**，然后**开新会话**。

清理完可以这样自查：`~/.zcode/hooks/` 应该是空的，`~/.zcode/agents/` 里不该再有那八个角色，`cli/config.json` 里搜不到 `teamwork`。

### 临时关掉文件独占锁

删掉目标项目里的 `.teamwork/campaign.json` 就行——**钩子在无 campaign 时完全空转**。

更正规的做法是 `/teamwork-end`：归档状态、解除钩子、顺手清掉可能残留的锁目录和 `.tmp`。
